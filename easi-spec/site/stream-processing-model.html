Stream Processing Model

EASI is stream-first by design. Pipelines are not only compositional contracts; they are deterministic streaming protocols where the parser emits lifecycle events, handlers consume and transform those events, and returned statuses control parser progression in real time.

Why Stream-First Matters

Incremental Processing

Large DICOM® payloads can be processed as data arrives instead of waiting for full materialization.

Deterministic Control

Status responses provide explicit flow control for continue, skip, jump, stop, and fail behavior.

Composable Runtime Policy

Validation, de-identification, transcoding, and mapping filters execute in one ordered stream.

Canonical Stream Protocol

Reader -> Parser -> Handler Chain -> Status -> Parser -> Reader (next bytes)

Normative Contract

For canonical DICOM® parsing, parser lifecycle events are the protocol backbone. Handler-returned statuses MUST be interpreted consistently to preserve deterministic stream behavior.

Parser-Handler Handshake

Step Parser Action Handler Response Parser Behavior
1 Emit lifecycle event (onStart*, onAppend*, onEnd*). Return status (or default continue). Normalize status and update stream flow state.
2 Continue parsing current structure. CONTINUE / SUCCESS Read next bytes and emit next deterministic event.
3 Encounter branchable subtree (sequence/item/segment). SKIP / JUMP Skip target scope using structural boundaries.
4 Receive terminal directive. STOP / FAIL Finalize safely or abort with structured error state.

Execution Contexts

Transactional

One request/source input, one streaming transaction, one result collection.

resultCollection := pipeline.process(source)

Listener

Source is transport-bound (for example DIMSE C-STORE SCP) and stream transactions arrive continuously.

run := pipeline.start(options)
... onResult per transaction ...
run.stop()
