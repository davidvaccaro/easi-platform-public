Standard Boundary

This page defines the line between language-neutral EASI standard semantics and implementation-specific details. The goal is interoperability without constraining runtime internals.

Boundary Rule

Normative Inclusion Test

A behavior belongs in the standard when independent implementations must do the same thing to remain interoperable. Internal data structures, helper classes, and runtime ergonomics remain implementation documentation.

What Is Normative vs Implementation Detail

Belongs In EASI Standard Belongs In Implementation Docs
Pipeline stage semantics and ordering. Class/file names (Runtime, PartStreamReader, etc.).
Lifecycle events and status semantics. Internal callback dispatch mechanisms.
Builder intent contract (from/of/with/to/into/build). Exact method casing and overload style per language.
Compatibility expectations and fail-fast composition behavior. Exception class hierarchies and stack trace formats.
Conformance claims and scenario definitions. Default logging adapters and telemetry frameworks.

Decision Framework

Question If Yes If No
Would divergence break cross-language behavior compatibility? Standardize as normative semantics. Keep as implementation detail.
Is this required for a conformance test to pass/fail reliably? Standardize assertion and expected outcome. Document as local implementation guidance.
Is this primarily naming/style ergonomics? Document only intent, not syntax. Allow language/runtime-specific expression.
Is this transport/runtime-specific infrastructure? Define extension profile contracts only. Keep internal implementation optional.

Change Control Guidance

Standard updates should prioritize semantic stability. Breaking semantic changes must increment major version and include migration guidance for conformance claims.

Implementation docs can evolve more rapidly as long as normative behavior and published conformance claims remain accurate.
