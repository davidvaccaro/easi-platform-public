Conformance

This page defines what it means for an implementation to conform to EASI. Conformance is capability-based and level-scoped so implementations can claim support progressively.

Conformance Model

Dimension Focus Requirement Type
Pipeline Conformance Reader/Parser/Adapter/Filter/Terminal/Writer semantics Normative
Lifecycle/Status Conformance Event ordering and status behavior (CONTINUE, SUCCESS, STOP, JUMP, FAIL) Normative
Builder Contract Conformance from..., of..., with..., to..., into..., build() intent Normative
Scenario Conformance Specific source/terminal/writer scenario support Normative when claimed
Streaming Behavior Conformance Incremental processing and bounded buffering behavior Normative when claimed

Conformance Levels

Level Label Minimum Required Capability
L1 Core API Conformance Pipeline model, lifecycle/status semantics, builder core, fail-fast build() validation.
L2 DICOM® Core Scenario Conformance Native DICOM® bytes to instance output, selection output, and mapping output.
L3 Extended Scenario Conformance Additional standardized scenarios such as DICOMweb™ metadata, de-identification, validation, re-emission, and extension transports.

Conformance Claim Rule

An implementation MUST NOT claim a level unless all mandatory requirements for that level are satisfied. Optional features MAY be claimed separately as extension profiles.

Mandatory Assertion Families

Assertion Family Examples Expected Verification
Ordering Lifecycle events occur in valid order; nesting closes in LIFO order. Deterministic event-trace fixtures.
Status Semantics STOP halts parse; JUMP skips target subtree; FAIL aborts with structured error. Status-focused edge-case fixtures.
Composition Invalid parser/terminal/writer compositions fail during build(). Negative build-composition tests.
Semantic Integrity Nested sequence behavior does not corrupt top-level attribute scope. Nested sequence regression fixtures.
Scenario Outcomes Claimed scenarios produce declared output type and structural validity. Scenario matrix test coverage.

Fixture Classes

Core Fixtures

Valid Part-10 instances, nested sequence edge cases, malformed/truncated inputs for strict and permissive behavior.

Metadata Fixtures

DICOM® JSON and XML metadata fixtures that normalize into canonical semantic events.

Scenario Fixtures

Source-to-output combinations aligned to the published scenario matrix and claimed capability profile.

Transport Fixtures

When extension profiles are claimed (for example DIMSE), include protocol/timeout/compatibility fixtures.

Language-Specific Allowances

Allowed To Vary Must Not Vary
Method casing and naming idioms. Pipeline semantics and stage responsibilities.
Async primitives and runtime scheduling model. Observable lifecycle ordering and status outcomes.
Byte container and stream abstraction types. Compatibility/error behavior guarantees.
