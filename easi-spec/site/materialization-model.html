Materialization Model

EASI stream processing can run in fully materializing, non-materializing, or hybrid modes. Choosing the right mode is a first-order design decision because it directly affects memory footprint, latency, and downstream workflow design.

Normative Intent

Conforming implementations must preserve the same functional semantics in both materializing and non-materializing paths. The difference is output realization strategy, not clinical/data meaning.

Definitions

Mode Behavior Typical Outcome
Materializing Pipeline accumulates output payloads in memory before returning. Convenient random access to full result objects/bytes.
Non-Materializing Pipeline emits chunks/events as data flows and avoids full payload accumulation. Lower peak memory and better steady-state streaming throughput.
Hybrid Small metadata may be materialized while large payloads remain streamed. Balanced observability and operational efficiency.

Control Points

Layer API Control Practical Effect
Terminal DICOM® bytes toDicomData({ collectOutput, onChunk }) Switch between full byte-array accumulation and chunk-native emission.
Asset payload extraction toAssets({ payload: { mode, onFrameChunk, onContentChunk, collect } }) Control frame/content payload materialization versus chunk streaming.
Parser bulk payload policy withBulkDataPolicy({ mode, knownLengthThreshold, hardSafetyCap }) Guide parser behavior for large value fields during stream parse.
Per-part emission withOnEmit(callback) or read options onEmit Process multipart results incrementally rather than aggregating externally.
Outbound destination streaming intoFileStream(...), intoNodeStreamAdapter(...), intoHttpStream(...) Stream terminal output to external sinks; useful for transport egress even when terminal output is materialized.

Stable Contract

When into* Is Used

Scenario resultCollection.first() Notes
Writer sink applied (for example intoFileStream, intoHttpStream) PipelineOperationResult (writer category) Includes stable fields (resultType, writer, bytesWritten, payload) plus writer-specific output fields.
toDicomData({ collectOutput:false, onChunk }) with into* PipelineOperationResult Pipeline keeps terminal chunk path; writer sink is intentionally not layered over it (operation="toDicomData", category="terminal").
Custom writer sink (non-built-in into* implementation) Writer-defined output Only built-in writers are normalized to PipelineOperationResult; custom writers return their native output contract.

Materializing Example

Materialize one full DICOM® byte output in-memory, then consume it as a contiguous payload. 

const pipeline = EASI.pipelineBuilder()
  .fromFileStream()
  .ofDicomData()
  .toDicomData() // collectOutput defaults to true
  .build();

const resultCollection = await pipeline.process({ source: "/var/easi/inbox/ct/CT-001.dcm" });
if (resultCollection.isEmpty) {
  return;
}

const dicomBytes = resultCollection.first(); // Uint8Array
await archiveClient.put("study/CT-001.dcm", dicomBytes);

Non-Materializing Example (Terminal Chunk Stream)

Emit DICOM® output bytes chunk-by-chunk and avoid full in-memory payload aggregation. 

let totalBytes = 0;

const pipeline = EASI.pipelineBuilder()
  .fromFileStream()
  .ofDicomData()
  .toDicomData({
    collectOutput: false,
    onChunk: async (chunk) => {
      totalBytes += chunk.length;
      await uploadStream.write(chunk);
    }
  })
  .build();

const resultCollection = await pipeline.process({ source: "/var/easi/inbox/ct/CT-001.dcm" });
const writeResult = resultCollection.first(); // PipelineOperationResult
const bytesWritten = writeResult.bytesWritten;
await uploadStream.close();

In this mode, toDicomData returns a standardized PipelineOperationResult with materialized=false and bytesWritten.

Important

When using collectOutput: false, provide a chunk sink (onChunk) or another explicit downstream handling strategy so payload bytes are not silently discarded.

Destination Stream Example (Writer Sink)

Route terminal output into a destination writer. This streams bytes to the sink, but terminal output may still be materialized first unless terminal chunk mode is used. 

const resultCollection = await EASI.pipelineBuilder()
  .fromFileStream()
  .ofDicomData()
  .toDicomData() // materialized terminal payload
  .intoFileStream("/var/easi/outbox/CT-001.dcm", {
    chunkSize: 16384,
    collectOutput: false
  })
  .build()
  .process({ source: "/var/easi/inbox/ct/CT-001.dcm" });

const writeResult = resultCollection.first();
const bytesWritten = writeResult.bytesWritten;

Design Note

into* controls outbound sink behavior. For true parser-to-terminal non-materialization, use terminal chunk mode (toDicomData({ collectOutput: false, onChunk })).

Hybrid Example

Keep metadata structured while streaming heavy frame payloads. 

const pipeline = EASI.pipelineBuilder()
  .fromFileStream()
  .ofDicomData()
  .withBulkDataPolicy({ mode: "stream", knownLengthThreshold: 512 * 1024 })
  .toAssets({
    metadata: {
      mapping: metadataMapping,
      collect: true
    },
    payload: {
      mode: "stream",
      frame: { frames: "all", decode: "native", encode: "none" },
      onFrameChunk: async ({ index, bytes, isFinalChunk }) => {
        await frameChunkSink.write(index, bytes, isFinalChunk);
      },
      collect: false
    }
  })
  .build();

const resultCollection = await pipeline.process({ source: "/var/easi/inbox/us/US-001.dcm" });
const result = resultCollection.first(); // { instanceUID, metadata } when metadata.collect !== false and payload.collect === false

Selection Guidance

Prefer Materializing

When payloads are moderate and downstream logic needs random access to complete results.

Prefer Non-Materializing

When handling large studies, long-running listeners, or continuous ingest with strict memory targets.

Prefer Hybrid

When metadata is needed synchronously but payload bytes should be streamed to external sinks.
