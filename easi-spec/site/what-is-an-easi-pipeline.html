What Is an EASI Pipeline?

An EASI pipeline is an expressive, staged data-processing contract for the orchastration of complex DICOM® workflows. It lets a developer compose source, parse mode, transformations, output form, and destination as one readable flow with deterministic execution semantics.

Normative Definition

A conforming EASI pipeline preserves stage order and responsibility boundaries: Reader -> Parser -> [Adapter] -> [Filter ...] -> Terminal -> [Writer]. Implementations may vary by language, but behavior and composition intent remain equivalent.

Stage Guide

The table below makes each stage explicit so a reader can quickly understand what each stage is responsible for and where each decision belongs.

Stage Builder Clause Primary Purpose Consumes Produces
Reader from... Acquire bytes/parts from a concrete source transport. Source handle or transport request (file path, URL, DIMSE request, stream). Ordered byte/part stream forwarded to parser.
Parser of... Decode source bytes into deterministic lifecycle events. Reader-emitted bytes/parts. Structured parse events (onStart..., onEnd..., chunk events).
Adapter (Optional) Selected implicitly by parser/terminal shape Bridge alternate parser domains into canonical DICOM® semantic flow. Parser events from JSON/XML metadata modes. Normalized semantic events compatible with DICOM-oriented filters/terminals.
Filter Chain (Optional) with... Apply in-flight policies and transformations without changing stage order. Canonical semantic events and payload chunks. Validated/de-identified/transcoded/redacted flow to terminal stage.
Terminal to... Materialize or stream the target output contract. Filtered semantic flow. Terminal result items (for example Instance, assets, bytes, mappings).
Writer (Optional) into... Deliver terminal output to a destination system. Terminal result payload. Destination write result envelope (for built-in writers) or writer-native result.

Why This Model Matters

Readable Intent

from..., of..., with..., to..., and into... clauses make purpose explicit at each stage.

Composable Power

The same model scales from one-shot reads to de-identification, transcoding, asset extraction, and transport relay.

Operational Consistency

Whether processing files, DICOMweb™, or DIMSE, result handling and lifecycle controls stay uniform.

Functional Range

Capability Tier Typical Composition Practical Outcome
Simple Read Access fromFileStream/fromHttpStream + ofDicomData + toInstances Read native DICOM® into typed instance objects.
Focused Data Access toSelection or toMapping Extract only needed tags or convert to domain/FHIR® views.
Privacy Processing withDeIdentification + optional burned-in redaction Apply deterministic PHI minimization in-flight.
Format Normalization withValidation + withTranscoding Enforce quality constraints and normalize transfer syntax.
Asset Extraction toAssets Produce frame data, structured metadata, and encapsulated content assets.
Delivery and Relay intoFileStream, intoHttpStream, or intoDimseAssociation Route outputs to archive, cloud APIs, or peer DICOM systems.
DIMSE Listener Workloads fromDimseAssociation + start() Run long-lived inbound C-STORE services with per-transaction processing.

Binding Modes

Binding describes when source and destination values are supplied: either at pipeline construction time, at transaction time, or a combination of both.

Mode What It Means Typical Builder Shape Typical Transaction Call
Early-Bound Source and destination are fixed when the pipeline is built. from*(source) + into*(destination) process()
Late-Bound Source and destination are provided per transaction. from*() + into*() process(source, destination)
Hybrid Destination is fixed at build time while source varies per transaction. from*() + into*(destination) process(source)

Execution Modes

Transactional Mode

Use process(...) for one complete transaction. Invocation shape follows binding mode: process() for early-bound pipelines, process(source) for source-late/hybrid pipelines, or process(source, destination) for fully late-bound pipelines. Each call returns one result collection. 

resultCollection := pipeline.process(source, destination)

Listener Mode

Use start() when source is bound by transport (for example DIMSE C-STORE SCP) and traffic arrives over time.

run := pipeline.start(options)
... handle inbound transactions ...
run.stop()

Unified Result Contract

Pipeline terminal outputs are returned as PipelineResultCollection for stable cardinality handling. Consumers can safely access first() for single-output flows or iterate collections for multi-output flows. See Pipeline Result Contract for the dedicated contract details.

Canonical Composition Pattern

pipeline := EASI.pipelineBuilder()
  .from<SourceFamily>(...)
  .of<ParseMode>(...)
  .with<FilterOrPolicy>(...)
  .to<TerminalContract>(...)
  .into<OptionalWriter>(...)
  .build()

resultCollection := pipeline.process(source)
if resultCollection.isEmpty():
  return noResult

result := resultCollection.first()
... continue with result ...

This pattern is intentionally stable across use cases: only stage choices change as requirements grow.
