Core Pipeline Model

This page defines the normative execution model for EASI pipelines. All conforming implementations must preserve these semantics even when language syntax differs.

Canonical Topology

Reader -> Parser -> [Adapter] -> [Filter ...] -> Terminal -> [Writer]

Normative Requirement

Conforming implementations MUST preserve stage ordering and data responsibility boundaries. Internal class names and object models MAY vary by language.

Component Contracts

Component Primary Responsibility Normative Notes
Reader Acquire source bytes/parts and forward parser-ready payloads. MUST isolate transport mechanics from parse semantics.
Parser Decode one source format incrementally into lifecycle events. MUST implement deterministic status-handling behavior.
Adapter Translate metadata syntaxes into canonical DICOM® semantic events. Required when parser event model is not canonical DICOM®-native.
Filter Apply ordered semantic transformations/validation. MUST preserve upstream semantics unless explicitly configured otherwise.
Terminal Materialize final output contract (instance/mapping/selection/assets). MUST be last semantic stage before optional writer packaging.
Writer Package terminal output for downstream transport or stream sinks. MAY be omitted if terminal output is final consumer payload.

Builder Intent Semantics

Intent Prefix Meaning Examples
from... Select source mode/transport family. fromHttpStream, fromPartStream, fromDimseAssociation
of... Select parse format behavior. ofDicomData, ofDicomMetadata
with... Apply explicit configuration and semantic filters. withDeIdentification, withValidation
to... Declare terminal output contract. toInstances, toMapping, toSelection
into... Apply output packaging/writer transport. intoByteBuffer, intoDimseAssociation
build() Compose and validate final pipeline. Must fail fast on invalid composition.

Pipeline Use-Case Gallery

The examples below show what pipelines are for, how they are composed, and how one fluent model supports common DICOM® workflows from simple reading through de-identification, transcoding, and asset extraction.

Execution failures surface as thrown exceptions from process(...). The samples also demonstrate contract-level success checks using resultCollection.first() (for example bytesWritten > 0 for writer paths; some writers also provide transport-specific fields such as ok and status).

Language-Neutral Examples

Typical use case: native DICOM® reader to instance output.

sourceUrl := "http://localhost:8042/dicom-web/studies/{studyUID}/series/{seriesUID}/instances/{instanceUID}"

readerPipeline := EASI.pipelineBuilder()
  .fromHttpStream()
  .ofDicomData()
  .toInstances()
  .build()

instanceCollection := readerPipeline.process(sourceUrl)
instance := instanceCollection.first()
studyUid := instance.dataSet.value(Tag.StudyInstanceUID)

Real-world use case: de-identify and write a clean DICOM® output file.

sourcePath := "/var/easi/inbox/ct/CT-001.dcm"
destinationPath := "out/deidentified.dcm"

deIdPipeline := EASI.pipelineBuilder()
  .fromFileStream()
  .ofDicomData()
  .withDeIdentification(Tag.DefaultDeIdentificationMask)
  .toDicomData()
  .intoFileStream()
  .build()

deIdResults := deIdPipeline.process(sourcePath, destinationPath)
deIdWrite := deIdResults.first()
if (deIdWrite == null) OR (deIdWrite.bytesWritten <= 0):
  fail("De-identification pipeline did not produce output bytes")

Real-world use case: strictly redact known burned-in overlay regions in a US image.

usSourcePath := "/var/easi/inbox/us/US-PAL-8-10x-echo.dcm"
usDestinationPath := "out/us-redacted.dcm"

usRedactionPipeline := EASI.pipelineBuilder()
  .fromFileStream()
  .ofDicomData()
  .withDeIdentification(Tag.DefaultDeIdentificationMask)
  .withBurnedInRedaction({
    mode: "regions",
    regions: [
      { x: 24, y: 10, width: 220, height: 40 },
      { x: 24, y: 54, width: 260, height: 30 }
    ]
  })
  .toDicomData()
  .intoFileStream()
  .build()

usRedactionResults := usRedactionPipeline.process(usSourcePath, usDestinationPath)
usRedactionWrite := usRedactionResults.first()
if (usRedactionWrite == null) OR (usRedactionWrite.bytesWritten <= 0):
  fail("US redaction pipeline did not produce output bytes")

Real-world use case: extract frames, metadata, and encapsulated content as non-DICOM assets.

sourcePath := "/var/easi/inbox/mr/MR-0001.dcm"

assetPipeline := EASI.pipelineBuilder()
  .fromFileStream()
  .ofDicomData()
  .toAssets({
    metadata: {
      mapping: DicomToFHIRImagingStudyMapping({ profile: "study-summary" }),
      collect: true
    },
    payload: {
      frame: { frames: "all", decode: "rgba", encode: "png" },
      collect: true
    }
  })
  .build()

assetsCollection := assetPipeline.process(sourcePath)
if assetsCollection.isEmpty:
  fail("Asset extraction emitted no results")
assets := assetsCollection.first()
if assets.instanceUID == null:
  fail("Asset extraction did not resolve instance UID")
frameCount := assets.frames.length
metadataCount := assets.metadata.length
contentCount := assets.content.length

Filter Composition Order

Default canonical ordering when multiple semantic filters are enabled:

Validation -> De-Identification -> Burned-In Redaction / Transcoding -> Terminal

Implementations MUST document any ordering differences and their behavioral impact. If a profile claims conformance with this order, the runtime behavior MUST match.

Extension Points

Custom Mapping

Mappings may define domain-specific projection behavior if they consume canonical semantic events and preserve lifecycle boundaries.

Custom Selection

Selection logic may be implementation-specific but SHOULD expose deterministic completion semantics.

Custom Filter

Filters MAY add profile-specific logic. They MUST not violate parser status semantics or break terminal contracts.

Custom Writer

Writers MAY package output for local files, HTTP, DIMSE, or stream adapters without redefining terminal semantics.

Result Contract

Result handling SHOULD begin with PipelineResultCollection, with optional PipelineOperationResult evaluation for operation-oriented outcomes.
