Pipeline Terminal

Terminals define the contract of what a pipeline emits after parsing and policy stages, including native DICOM® outputs, mapped projections, selections, entities, and assets.

Purpose

Terminal selection declares the expected output shape for each processing transaction. It is the semantic handoff between interpretation/policy stages and optional delivery stages.

Normative Requirement

Terminal contracts MUST be deterministic for a given parser stream and policy profile, and MUST return outcomes through the canonical PipelineResultCollection shape.

Core Concepts

Concept Core EASI Semantics
Output Contract Each terminal defines exactly what semantic payload is produced at transaction completion (instance, entity set, mapping object, selection set, etc.).
Materialization Depth Different terminals materialize different semantic depths, from targeted selection to full native instance representation.
Deterministic Completion Terminal completion semantics must remain predictable regardless of destination packaging behavior.
Writer Interop Delivery surfaces (into*) can package terminal output without changing terminal contract semantics.
Result Envelope Terminal output is exposed via PipelineResultCollection, with optional operation-level envelopes for destination-aware workflows.

Builder Surface

Builder Surface Terminal Contract Typical Use
toInstances() Native instance object model Canonical native materialization for broad DICOM® workflows.
toEntities() Entity projection contract Higher-level entity workflows and semantic business logic.
toDicomData() Native byte-oriented DICOM® output Transformation flows that return DICOM® output for storage/relay.
toMapping(mapping) Custom mapped output Generic domain projection contracts and custom operational models.
toUnwrappedDocuments(...) Typed unwrapped document output Extract encapsulated document payloads (for example PDF/text/media) with explicit metadata.
toWrappedDocuments(...) Wrapped native DICOM® document bytes Preserve wrapped document payloads for archive relay and native byte-level handoff.
toFHIRImagingStudy(...) FHIR® ImagingStudy projection FHIR-focused interoperability workflows and study-centric clinical indexing.
toStructuredValue() Structured syntax output (JSON/XML value model) Non-DICOM structured parser flows that emit normalized syntax objects.
toImageData(...) Normalized single-image payload output Single-image processing pipelines requiring one canonical image payload contract.
toImagingData(...) Mixed imaging payload output Unified routing for mixed native DICOM® and standard imaging source flows.
toAssets(...) Extracted imaging asset contract Frame/content extraction workflows with optional metadata materialization control.
toAssetArchive(...) Packaged imaging asset archive output Bundle extracted assets into archive artifacts for transfer, storage, or downstream processing.
toSelection(selection) Targeted attribute/value extraction Metadata-first indexing, routing, and lightweight decisions.

Usage

Terminal declarations are the contract center of pipeline composition: readers/parsers define ingress semantics, terminals define output semantics, and writers define delivery semantics.

Language-Neutral Examples

Entity terminal for semantic downstream workflows.

entityPipeline := EASI.pipelineBuilder()
  .fromHttpStream()
  .ofDicomData()
  .toEntities()
  .build()

entityResults := entityPipeline.process(sourceUrl)
entities := entityResults.first()

DICOM terminal plus writer for outbound relay.

relayPipeline := EASI.pipelineBuilder()
  .fromFileStream()
  .ofDicomData()
  .withDeIdentification(Tag.DefaultDeIdentificationMask)
  .toDicomData()
  .intoHttpStream({ endpoint: outboundStowEndpoint })
  .build()

relayResults := relayPipeline.process(sourcePath)
relayOutcome := relayResults.first()

Terminal Design Notes

  • Select the narrowest terminal that satisfies downstream contract requirements.
  • Use writer surfaces to deliver terminal output without redefining terminal semantics.
  • Prefer stable result shapes so operational handling remains predictable.
  • Document terminal completion expectations when adding custom contracts.
